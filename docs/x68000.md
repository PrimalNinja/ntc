# NTC on the Sharp X68000 (`x68000`)

The X68000 is a 68000 machine (10 MHz, 1 MB of RAM or more, 128 sprites, two tile layers,
bitmap layers, FM and sample sound). NTC builds for it with the same 68000 keyword library
and compiler path as the Mega Drive (`docs/md.md` section 1 says how NTC works on a 68000:
the thread is A7 in user mode, interrupts are on all the time, there is one mode, Integer
is 16 bits, Long 32).

**State: games run.** A program boots from its own floppy image, has the text console, the
keyboard, Frame and Ticks, and since 20261119-1 the classes a game needs (section 4):
sprites, a scrolling picture with raster splits and words (`Vdp`), held keys and joysticks
(`Keys`), ADPCM music (`Pcm`) and the FM chip (`Opm`). They were lifted from TIANLONG, the
first game written for the machine. It runs NTC's self tests and that game on the px68k
emulator with Sharp's ROM. There is no file class, no Human68k `.X` program, and nothing has
run on a real X68000.

## 1. What a program is

A 2HD floppy image, `.XDF`: 77 tracks, 2 sides, 8 sectors of 1024 bytes (1261568 bytes).
The machine's ROM reads the first sector to `$2000` and runs it (its first byte must be
`$60`, a branch). That sector is NTC's: it reads the rest of the program with the ROM's
disc call and starts it. Human68k is not on the disc and is not needed.

## 2. Memory

| Addresses | What |
|---|---|
| `$000000-$001FFF` | the 68000's vectors, the ROM's (IOCS) work area and stack |
| `$002000-$0023FF` | the boot sector |
| `$002400-$007FFF` | the program's variables, the library's, then its arrays: 23K |
| `$008000-$00FFFF` | the real stack (the library's `jsr` calls), from the top down |
| `$010000-` | the program: start code, threads, keywords, strings |

- **Variables and arrays have 23K.** On the 68000 NTC keeps a variable's address in 16
  bits, so they must be below `$8000`. `Peek`, `Poke`, `VarPtr` and array descriptors
  reach `$0000-$7FFF` only (`&H8000` and above mean the end of memory, which is ROM).
- **Code and strings have the rest of RAM** (up to the disc's size, 1.2 MB).
- **User mode.** The X68000 keeps its hardware registers and video memory for
  supervisor mode. The console and keys go through the ROM's calls (IOCS, `trap #15`),
  which work from user mode. `#asm` that touches hardware directly must use an IOCS call
  or change mode first (IOCS `_B_SUPER`, call `$81`).

## 3. The console, keys, Frame and Ticks

- **Screen:** the ROM's text screen, 96 x 32 characters on 768 x 512, the ROM's font.
  `Print`, `Cls`, `Locate`, `Mode` (one mode: it clears) and scrolling work.
- **Keys:** `Inkey`, `Inkey$` and `Input` read the keyboard. A key gives its character;
  the cursor keys give `&HF0 &HF1 &HF2 &HF3` (up, down, left, right, as on the CPC),
  Return 13, ESC 27.
- **Frame** waits for the vertical blank. **Ticks** counts frames: 55 a second on this
  screen (`System.TicksPerSecond`).
- **End / Stop:** the program stops and stays; a boot disc has nowhere to go back to.

Classes: `StdIO` and `System` (`lib/x68000/`), and the games' classes below.

## 4. The classes for games (`lib/x68000/`), and the supervisor call

The X68000 keeps its video, sound and I/O registers for supervisor mode, and an NTC program
runs in user mode. The platform's **supervisor call** is trap #1: from `#asm`,

```
            lea my_routine, a0
            trap #1
```

`my_routine` runs in supervisor mode on the supervisor stack and ends with `rts`. Interrupts
stay on. The ROM's calls (IOCS, `trap #15`) work from user mode as they are.

| Class | Members |
|---|---|
| `Keys` | `Down(key)`: True while the key is held (`Keys.KeyQ`, `KeyLeft`, `KeySpace` ...: the same names as on the Next), `Group(g)`. `Joystick(n)`: joystick n + 1 as `JoyUp`, `JoyDown`, `JoyLeft`, `JoyRight`, `JoyFire1` (A), `JoyFire2` (B) |
| `Vdp` | the screen: 256 x 256 in 256 colours (15 kHz). `Init`. Sprites: `Sat()` (the table's address: 128 x 4 words, as the hardware's), `Sprite n, x, y, c, p`, `HideAll`, `Update`, `Pcg addr&, first, n` (patterns, 128 bytes each), `Colors addr&, first, n`. Graphics page 0: `GColors addr&, first, n`, `GLoad addr&, y, n`, `GFill y, n, c`, `GPixel(x, y)`, `GPlot x, y, c`, `Split k, line, x` and `Splits n` (up to 4 raster splits, each with its own scroll), `Upload x` (after Frame: the top's scroll, the sprites). The text plane: `Font addr&`, `Text cx, cy, s$, c, shadow, bg`, `TFill cx, cy, w, h, c` |
| `Pcm` | `Init data&` (songs made by `tools/adpcm/okiadpcm.js --target=x68000`), `Have(n)`, `Play n, loop`, `Quiet`, `Update` (once a frame) |
| `Opm` | the YM2151: `Reg r, v`, `Quiet` |

## 5. Building and testing

Tools (none are part of NTC):

- **vasm** (68000, Motorola syntax): `make CPU=m68k SYNTAX=mot` gives `vasmm68k_mot`.
  `NTC_VASM` is its path.
- **px68k libretro core:** `github.com/libretro/px68k-libretro`, `make -f
  Makefile.libretro` gives `px68k_libretro.so`. `NTC_X68CORE` is its path.
- **Sharp's ROMs:** `iplrom.dat` and `cgrom.dat` in a folder named `keropi`.
  `NTC_X68SYS` is the folder that holds `keropi`.

```
node test/x68build.js Main.bas [More.cls ...] --out=GAME.xdf [--log]
python3 test/x68run.py GAME.xdf [--frames=N] [--keys=frame:text,...] [--shot=out.png] [--log] [--untilend]
bash test/x68regress.sh
```

- `x68build.js` compiles (`--platform=x68000`), assembles with vasm (`-Fbin -coalesced`)
  and writes the disc image. `--log` makes a test build that keeps what the console
  prints in RAM from `$0F0000`.
- `x68run.py` boots the disc on the core with no window: it types keys by a script
  (`\n` is Return, a capital is typed with Shift), saves a picture, and prints a `--log`
  build's transcript.
- `x68regress.sh` runs the self tests (vb_test, vb_test2-4, 6-9, long, argfn, class,
  sieve, guide), `test/x68/Main.bas` (typed input, Inkey, Ticks, Locate) and
  `test/towns/Extra.bas` (keywords the self tests do not reach; the same text as on the FM
  Towns), and `test/x68/Classes.bas` (the supervisor call and the Keys, Opm and Vdp classes):
  16 tests.

## 6. In the compiler and library

- `;@ramorg` (platform header): where a 68000 platform's variables are assembled. The
  Mega Drive's default is `$FF8000`; the X68000 says `$2400`.
- `;@ramend`: the end of that RAM; the compiler writes it as `NTC_RAMEND`, and the
  start-of-program array check (`kw_bssinit`) uses it (it was a fixed `$01000000`).
- The platform's first section is still named `ntc_md_vectors` (the 68000 path's name
  for "what comes first"): here it is the boot sector.
- vasm writes the parts of the file in address order: the boot sector (`$2000`), the
  variables' first image (`$2400`), then the code (`$10000`). The boot sector reads all
  that follows it to just below `$10000`, so the code lands where it runs, and the start
  code copies the variables' image down to `$2400`.

## 7. Not done

- The two tile layers (BG planes), the other graphics pages, files, the mouse.
- The boot loads the whole disc before the program starts (about 20 seconds in px68k for a
  full disc).
- A Human68k `.X` program (vasm can write that format).
- More than 23K of variables and arrays (needs 32 bit variable addresses on the 68000).
- A run on a real X68000 or another emulator.
