# The Enterprise 128 platform (`ep128`)

(c) 2026 Cyborg Unicorn Pty Ltd - MIT License

**Status (2026-11-25): first stage, run on an emulator only.** A Z80 program file that EXOS
loads and that then takes the machine and works the hardware itself. In it: the start, all of
the machine's memory (128K to 4 MB) as the `Memory` class's pages, the console in 40 and 80
columns, the keyboard, the three joysticks, the frame interrupt. Not in it yet: files,
graphics and sound classes (section 9).

It has run on the ep128emu emulator (EXOS 2.0, 2.1 and 2.4, 128K to 3.7 MB). It has not run on
a real Enterprise.

## 1. What a program is

- One file, `GAME.COM`: EXOS's 16 byte header, then the program. The header is `0, 5`, the
  program's length (low byte, high byte), then 12 zeros. Type 5 means "load at `#0100` and start
  there". The header is assembled with the program, so the assembler writes the finished file:
  `sjasmplus --raw=GAME.COM game.asm`.
- It loads like any Enterprise program: `LOAD "GAME.COM"` from IS-BASIC, or `:LOAD GAME.COM`
  from EXDOS - off a disc, or off an SD card adapter.
- `test/epbuild.js --img` also writes `GAME.IMG`: a 720K EXDOS disc (the PC's format) with
  `GAME.COM` and an `EXDOS.INI` holding the one line `LOAD GAME.COM`. EXDOS runs that file
  when the machine starts, so the disc starts the program by itself, after a key at the title
  screen.
- At most 48,896 bytes of program (`#0100`-`#BFFF`): EXOS loads no more than that.
- EXOS loads it and is asked once, at the start, for all of its free memory. After that the
  program has the machine: its own screen, keyboard and interrupt. EXOS is not called again.
- EXOS's own memory (its system segment) is not touched, so a later version can go back to
  EXOS for files.
- `End` starts the machine again (EXOS's cold start). A program that wants its last screen
  read waits for a key first.

## 2. Memory

The Enterprise's memory is 16K **segments**, numbered 0-255. The Z80 sees four of them at a
time, one in each 16K **page** (ports `#B0`-`#B3`). A 128K machine has 8 RAM segments
(`#F8`-`#FF`); a full machine has 4 MB.

| Page | Addresses | What NTC puts there |
|---|---|---|
| 0 | `#0000`-`#3FFF` | the program (the segment EXOS loaded it into); the interrupt handler's jump at `#0038` |
| 1 | `#4000`-`#7FFF` | the program and its arrays - and the `Memory` class's window (section 3) |
| 2 | `#8000`-`#BFFF` | the program and its arrays (to `#BCEF`); the start code's notes `#BCF0`-`#BCFF`; the list of segments `#BD00`-`#BDFF`; the stack `#BE00`-`#BFFF` |
| 3 | `#C000`-`#FFFF` | the screen's segment: the picture from `#C000`, the line table at `#FF00` |

So a program and its arrays have `#0100`-`#BCEF`: about 47K.

**The least it runs on is 128K.** At the start the program needs three free segments besides
its own, and one of them must be a video segment (`#FC`-`#FF`). An Enterprise 64 with no added
RAM has two. There the program stops at once with a red border.

### The start, step by step

1. EXOS has loaded the file and jumps to `#0100`.
2. The start code moves the stack to `#0100` down and turns Dave's interrupt sources off. (The
   stack EXOS leaves is its own: a call to EXOS made on it never comes back.)
3. It finds the program's own segments. EXOS leaves the first in page 0 and the **last** one
   it loaded in page 1. For a program over 32K that is the third part, and the second part's
   segment is in no page at all. The start code finds it by asking EXOS to free each segment
   number in turn: the only one EXOS agrees to free is that one.
4. It asks EXOS for every free segment (function 24) and lists them at `#BD00`. The segment
   EXOS shares with its own data is handed back.
5. The highest segment in the list becomes the screen's.
6. The screen's segment into page 3, NTC's line table given to Nick. The machine is the
   program's.

The start code is the first thing in the file (straight after `#0100`), so it is in page 0
whatever the program's size. This was worked out on EXOS 2.1 and also runs on 2.0 and 2.4.

## 3. All of the memory: `Option Memory Heap Pages`

```
Option Memory Heap Pages
```

With that line the `Memory` class hands out every free segment as a 16K **page**, switched into
the window `#4000`-`#7FFF` (page 1) when it is used - the same class, calls and far pointers as
on the Amstrad CPC and MSX-DOS 2, so a program written for those builds here unchanged.

- Page 1 is the program's own `#4000`-`#7FFF`. Pages 2 on are the free segments.
- Every segment is a page: 128K gives 3 more pages, 1 MB gives 59, 4 MB about 250.
- `Memory.FreePages()` says how many are free. `Memory.RamSize()` gives the machine's RAM in K
  (the free segments, the program's three, the screen's and EXOS's own).
- `Memory.AllocPage(Memory.TypeUser)` takes a page; `Memory.SelectPage(page)` puts it in the
  window and gives the window's address; `Memory.Alloc(bytes)` / `Free` are a heap over pages;
  `ReadByte`, `WriteWord`, `Copy` work through far pointers (page * 65536 + address).
- Banks (`AllocBank`, `BankPage`) are four pages, as on the CPC. `Memory.Banks()` counts whole
  banks only. `Memory.Pages()` counts in fours, so it can be up to three more than the pages
  there really are: the missing ones read as taken and are never handed out.
- There is no `CallBank`: a segment goes into the window, the whole 64K is never swapped.
- `System.Segments()` gives the free segments found at the start; `System.Segment(n)` the
  segment in page n now.

**A program over 16K that uses pages** must stay out of the window, as on the CPC:

```
Option Memory Reserved &H4000, &H4000
Option Memory Heap Pages
```

The compiler then builds the program in two parts, `#0100`-`#3FFF` and `#8000`-`#BCEF` (about
31K of program), with the window between them free for pages. No single Sub or the main
program can be bigger than one part.

Without `Option Memory Heap Pages` the default is `Heap Main`: `Memory.Alloc` hands out the
free RAM below `#BCF0` and no paging code is in the program. The free segments are still taken
at the start; they are just not used.

## 4. The console

- Nick, two colours (white on black), 25 rows of 8 lines, NTC's own font (characters 32-126).
- `Mode 1` (the start): 40 columns. `Mode 2`: 80 columns. `Mode 0` is 1, `Mode 3` is 2.
- The picture is a plain bitmap at `#C000`: one byte is one character's 8 pixels, 40 or 80
  bytes a line, 200 lines. A program can draw in it with `Poke`.
- The line table at `#FF00` is seven 16 byte blocks: the picture, the bottom border, the
  frame's sync (with the interrupt), the top border - 312 lines, 50 frames a second.
- `Print`, `Locate`, `Cls`, `Tab`, `Input`, `Inkey$`, `Line Input` as on every platform.

## 5. Keys and joysticks

- `Input` / `Inkey$` read the keyboard matrix (port `#B5`): letters, digits, the shifted
  signs as printed on the keys (Shift-3 gives `#`), ENTER, ERASE and DEL (both delete), ESC,
  TAB. No auto repeat. The function keys, STOP, HOLD, INS and the cursor keys give nothing
  to `Inkey$`: read them with `Keys.Down`.
- `Keys.Down(key)`: True while that key is held. The key numbers are the matrix's (row * 8 +
  bit); the class names the usual ones: `KeyUp`, `KeyDown`, `KeyLeft`, `KeyRight`, `KeySpace`,
  `KeyEnter`, `KeyEsc`, `KeyShift`, `KeyControl`, `KeyAlt`, `KeyStop`, `KeyHold`, `KeyF1` -
  `KeyF8`, `KeyQ`, `KeyA`, `KeyO`, `KeyP`, `KeyZ`, `KeyX` and more.
- `Keys.Joystick(0)`: the built in joystick (it is the cursor keys; fire is Space).
  `Keys.Joystick(1)` and `Keys.Joystick(2)`: the two control ports.
  The bits are the other machines': `JoyUp` 1, `JoyDown` 2, `JoyLeft` 4, `JoyRight` 8,
  `JoyFire1` 32.

## 6. Interrupts and time

- Normal mode: Nick's frame interrupt through Dave (INT1), 50 a second, IM 1, the handler at
  `#0038`. `Ticks` and `System.Ticks()` count them (`System.TicksPerSecond` is 50).
- `Frame` waits for the next frame, in turbo mode too (it reads the frame line from Dave).
- The `Interrupt` statement (a hook Sub) and interrupt classes (`Option Class Interrupt`)
  work as on the CPC, at 50 a second.
- The Enterprise has no way to force an interrupt from outside: no NMI button.

## 7. Building

```
node test/epbuild.js Main.bas [More.cls ...] --out=GAME.COM --img
```

- Needs node and sjasmplus (on the PATH, or `SJASMPLUS` gives its path).
- Writes `GAME.COM` (and `GAME.asm`, `GAME.sym` beside it).
- `--img`: also `GAME.IMG`, the 720K disc that starts the program by itself (section 1).
- `--log`: a test build. What the console prints is also kept in a segment of its own, for
  `eprun.py --log`. `End` then stops the machine instead of starting it again.
- `--ram=K`: also writes `GAME.ep128cfg` for the emulator (the machine's RAM in K).
- Other options (`--turbo` ...) go on to the compiler.
- Without the tool: pick `ep128` in the web IDE (or `cli.js --platform=ep128`), then
  `sjasmplus --raw=GAME.COM game.asm`. That file is complete.
- In a program: `#If NTC_EP128 Then` ... `#End If` for lines only this platform gets.

## 8. Testing on the emulator

```
python3 test/eprun.py GAME.IMG --log --untilend
python3 test/eprun.py GAME.IMG --frames=1500 --keys=+100:hello\n --shot=out.png
```

- The emulator is the ep128emu libretro core: `git clone https://github.com/libretro/ep128emu-core`,
  `make`, and `NTC_EPCORE` set to the `.so`. It carries EXOS, IS-BASIC and EXDOS itself.
- `eprun.py` starts an Enterprise 128 with the disc in its drive, presses a key at the title
  screen, types keys (`--keys`), holds a key (`--hold=frame:q`, `--hold=frame:up`), holds a
  joystick (`--joy`, `--joy2`), saves the picture (`--shot`) and prints a `--log` build's text.
- A frame number written `+n` is n frames after the program started. A bigger machine tests
  its RAM for longer, so the start is not at a fixed frame.
- `eprun.py GAME.COM` runs the file alone: the emulator's own file device and IS-BASIC's
  `START`. It works most times. But that device sometimes hands a program over wrongly - one
  program of exactly 5,334 bytes failed nearly every time, and the same file off the disc never
  did. The fault is before a single byte of the program has run. So the tests use the disc.
- For machines over about 448K the core must be built with two numbers raised, as the top
  of `eprun.py` says. Without that the script cannot see all of the machine's RAM.
- `bash test/epregress.sh` runs 32 checks: the language self tests, typed input, the
  Interrupt hook, interrupt classes, programs of 26K and 45K, the `Memory` class on 128K to
  3.7 MB (every segment marked and read back), a 64K machine refused, keys, the three
  joysticks, 80 columns, and the `.COM` alone from IS-BASIC.
- Also run by hand, not in the script: EXOS 2.0 (an Enterprise 64 with 256K) and EXOS 2.4.
  Both start a 45K program and find all their segments.

## 9. Not done yet

- **Files.** No `FileSystem` or `Loader` class yet: the program is one file of up to 47K
  (plus what it builds in its pages). The way in is left open: EXOS's system segment is
  untouched, so a loader can put EXOS back for the length of a call.
- **Graphics.** Nick's 4, 16 and 256 colour modes, the palette, the border: no class yet. The
  console's bitmap can be drawn in with `Poke`.
- **Sound.** Dave's three tone channels and noise: no class yet.
- **A real machine.** Everything here is from the emulator. Not checked on hardware: the
  keyboard port's other bits (tape, printer), real drives and SD card adapters.
- **Overlay classes** (code loaded into pages) need files first.
